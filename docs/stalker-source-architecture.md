# Целевая архитектура подключений и навыков STALKER

Статус на 6 ноября 2026: `apps/auth` и совместная сборка для GitHub Pages реализованы; [параметры подключения](auth.md). Нативный обработчик входа, адаптеры источников, навыки сбора и воспроизведение стиля остаются проектом. Текущие десять workspace-пакетов и их зависимости находятся в проверяемом виде `modules`; будущие компоненты выделены в LikeC4 как `proposed-*`.

PROTEUS получает выбранный пользователем чат, пост, страницу или репозиторий, собирает доступный материал и формирует проверяемые свидетельства для архетипа, навыков, манеры рассуждать и оформления речи. Авторизация и загрузка принадлежат нативному приложению. STALKER самостоятельно выбирает действия в пределах разрешённого источника; инструкции навыка не расширяют доступ.

## Размещение приложений

`apps/auth` — приватный пакет `@proteus-int/auth` на SolidJS и Vite. Это небольшое статическое SPA с состояниями получения callback, ошибки и возврата в PROTEUS. LikeC4 генерирует отдельный статический сайт. Оба результата собираются в один артефакт публикации:

```text
<site-root>/
  architecture/   ← сборка LikeC4
  auth/           ← сборка apps/auth, физический index.html
```

Для GitHub Pages проекта префикс — `/proteus/`: Vite использует `/proteus/auth/`, LikeC4 — `/proteus/architecture/`. Callback имеет постоянный адрес `https://gnoy-i-salo.github.io/proteus/auth/`; его доступность подтверждается после успешной публикации. LikeC4 не является сервером авторизации.

Workflow CI собирает обе части, проверяет вложенные пути и публикует их совместно из `trunk` после JavaScript, браузерных и всех нативных проверок. PR только проверяет сборку. Два независимых деплоя на один Pages-сайт не используются, чтобы один не заменил файлы другого. В auth нет аналитики, внешних скриптов, localStorage или service worker. Разные пути одного origin не дают изоляции: service worker документации, если появится, ограничивается `/architecture/`.

`auth → contracts` — единственная workspace-зависимость нового приложения. `desktop` и `auth` не импортируют друг друга. Контракты содержат версионированный формат callback и статусы, но не секреты. Будущие нативные Rust DTO должны проверяться на совместимость с этими форматами. Пакет, manifests и действующая модель зависимостей обновляются одновременно.

## Нативная граница и хранение

В Rust host добавляется служба источников с адаптерами Telegram, VK, GitHub, Instagram и файлового импорта. Она отвечает за подключение аккаунта, проверку разрешений, загрузку, пагинацию, ограничения запросов, отмену и возобновление. Отдельный Node-сервер не требуется.

Токены, ключи шифрования и краткоживущие транзакции входа хранятся в системном хранилище секретов. Корпус — отдельная зашифрованная локальная база, целевой вариант SQLCipher; база TDLib использует собственное шифрование. Frontend получает статусы подключения и выбранные данные, а модель — только разрешённые результаты инструментов. Секреты не попадают в URL артефактов, журналы, экспорт или инструкции модели. Авторизация установленных Codex/Kimi CLI остаётся у самих CLI.

Связь с доменом — типизированный `SourcePort` из `contracts`. Desktop передаёт реализацию через pipeline; STALKER не импортирует Tauri и не обращается к платформам напрямую. Нативный сервис проверяет каждое действие независимо от проверки TypeScript. Отзыв аккаунта, удаление локального корпуса и отмена задания — отдельные операции.

## Telegram через TDLib

Встраиваем TDLib в Rust-приложение через C ABI, целевой вариант — статическая линковка `tdjson_static` с платформенными зависимостями. Авторизация, её состояния и обновления обрабатываются нативно; `apps/auth` в этом процессе не участвует. Для приложения нужны `api_id` и `api_hash`. Пользователь входит, выбирает чат или канал, участника и период. Загрузка сохраняет авторство, ответы, пересылки, временные метки и точки продолжения. [TDLib](https://core.telegram.org/tdlib/getting-started), [сборка библиотеки](https://github.com/tdlib/td).

TDLib — полноценный клиент, поэтому ограничения чтения задаёт наш allowlist, а не OAuth scope. Отправка и удаление сообщений отсутствуют в инструментах STALKER. Загружается только история, доступная этой сессии; скрытое, удалённое и секретные чаты другой сессии не считаются доступными. Для AI-обработки учитываются отдельные условия Telegram о допустимом использовании материала и согласии участников; доступ к чату сам по себе не даёт универсального разрешения. [Условия использования контента Telegram](https://telegram.org/tos/content-licensing).

## VK через статический callback

Выбираем Web-регистрацию и Authorization Code с PKCE как целевую интеграцию. Официальный VK SDK выполняет обмен кода с `code_verifier`, `device_id`, `state`, `client_id` и `redirect_uri` без `client_secret`; это основание для нативного обмена. Доступность нужных VK API методов проверяется отдельно после подключения. [Исходный код VK ID SDK](https://github.com/VKCOM/vkid-web-sdk/blob/master/src/auth/auth.ts).

1. Rust создаёт случайный `state`, PKCE verifier и challenge. Сохраняет ожидаемый provider, точные client ID и redirect URI, срок жизни и состояние транзакции. Pending-транзакция защищена нативным хранилищем, чтобы возврат мог запустить закрытое приложение.
2. Desktop открывает VK ID в системном браузере. Ожидаемое значение `state` и verifier остаются в Rust; `state` и challenge передаются провайдеру.
3. VK возвращает браузер на точный HTTPS callback вида `<site-root>/auth/?code=…&device_id=…&state=…`. Регистрируется реальный каталог с завершающим `/`, без fragment и без несуществующего SPA-маршрута `/callback`.
4. SPA читает только разрешённые поля, очищает адрес через `history.replaceState` и предлагает открыть фиксированную ссылку приложения, например `proteus://oauth/vk?...`. Произвольного `return_to` нет. Ранний `no-referrer` и ограниченная политика скриптов уменьшают утечки; короткоживущий код всё равно проходит через инфраструктуру хостинга.
5. Rust проверяет схему и путь ссылки, provider, ожидаемый state, срок, обязательные поля, дубликаты и однократность. Callback не может передать свои token endpoint, client ID или redirect URI. Затем Rust обменивает код с сохранённым verifier и исходным HTTPS redirect URI, проверяет аккаунт и сохраняет токены.
6. Desktop показывает результат и реальные доступные функции. SPA показывает только факт передачи: она не знает, завершился ли обмен успешно.

Нативный маршрутизатор различает callback и существующее открытие `.proteus`. Нужны проверки возврата при запущенном и закрытом приложении на всех ОС; Tauri поддерживает оба сценария с соответствующей регистрацией. [Deep linking Tauri](https://v2.tauri.app/plugin/deep-linking/), [OAuth для нативных приложений](https://www.rfc-editor.org/rfc/rfc8252.html).

После входа адаптер отдельно проверяет профиль, выбранные посты и комментарии; личные сообщения доступны только при реально выданном доступе приложения. Отказ метода, пустой ответ и успешная загрузка — разные состояния. Авторизация VK ID не считается доказательством доступа ко всем данным VK. Полный вход и права конкретной новой регистрации должны пройти интеграционный тест.

## Instagram без обязательного сервера

| Способ                              | Назначение и границы                                                                                                                                                                                                     |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Импорт архива или выбранного текста | Основной путь для личного аккаунта и предоставленной переписки. Архив пользователя не содержит всю чужую страницу.                                                                                                       |
| API собственного Business/Creator   | Пользователь получает токен через Meta App Dashboard; защищённый нативный ввод передаёт его в хранилище Rust. Далее адаптер читает разрешённые данные подключённого аккаунта и обновляет действующий долгосрочный токен. |
| Чтение выбранной страницы           | Экспериментальный адаптер отдельного системного WebView: собственная сессия, выбранный доступный материал и предпросмотр импорта. Полнота ограничена реально загруженным содержимым.                                     |

Официальный путь экспорта: настройки Instagram → Центр аккаунтов → информация и разрешения → экспорт информации → экспорт на устройство. Парсер определяется по реальной версии архива и fixtures. [Экспорт Instagram](https://help.instagram.com/181231772500920).

Токен собственного профессионального аккаунта можно получить через Instagram API setup в Meta App Dashboard. Это персональная настройка, а не универсальный OAuth для всех пользователей. API не даёт историю произвольного личного профиля. Для стандартного Instagram OAuth обмен кода и получение долгосрочного токена требуют конфиденциального серверного секрета: Meta прямо запрещает встраивать его в распространяемый клиент. Такой backend остаётся отдельным будущим решением, не частью базовой архитектуры. [Выдача токена](https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-instagram-login/get-started), [Business Login и обновление токена](https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-instagram-login/business-login).

Вариант чтения страницы сначала проходит проверку совместимости входа и извлечения на каждой ОС. Удалённый WebView не получает команд Tauri, доступных основному интерфейсу; мост захвата принимает только ограниченный снимок выбранного материала и проверяет его в Rust. Cookies и пароли не передаются агенту. Нет обхода CAPTCHA, скрытых API или автоматического расширения сбора на весь аккаунт. Авторизованный просмотр сам по себе не означает разрешение платформы на массовый скрапинг. [Изоляция Tauri](https://v2.tauri.app/security/capabilities/), [позиция Meta по автоматическому сбору](https://about.fb.com/news/2022/07/actions-against-scraping-for-hire/).

Playwright не включается в базовый вариант: системный WKWebView на macOS не равен браузеру Playwright. Универсальная автоматизация потребует собственного runtime и совместимых браузеров; их можно положить в установщик, но это дополнительные исполняемые компоненты. Резервный путь — системный браузер и импорт выбранного текста. [Браузеры Playwright](https://playwright.dev/docs/browsers), [WebView2](https://playwright.dev/docs/webview2).

## GitHub

Используем GitHub App с device flow и минимальными разрешениями чтения нужных репозиториев. Rust открывает страницу подтверждения, ожидает выдачу и хранит токен; callback SPA не нужен. Материал для STALKER — выбранные репозитории, код, README, issues, PR и обсуждения, доступные аккаунту. API-пагинация и ограничения происхождения событий учитываются в покрытии. [Токен пользователя GitHub App](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app).

## Навыки и самостоятельный сбор агентом

Проектируем четыре навыка внутри STALKER: `telegram-research`, `vk-research`, `instagram-research`, `github-research`. Будущие инструкции размещаются в `packages/stalker/skills/<skill-name>/SKILL.md` и включаются в сборку. Это навыки исследовательского агента; они отделены от task-skills создаваемой персоны.

| Навык     | Что агент выбирает и проверяет                                                                                                             |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Telegram  | Нужные сообщения выбранного чата, поисковые запросы, контекст ответов; собственная речь отдельно от цитат и пересылок.                     |
| VK        | Выбранный пост, комментарии и ответы, авторство; недоступные методы отмечаются, права не предполагаются.                                   |
| Instagram | Доступный режим: архив, профессиональный API или разрешённый снимок страницы; загруженные комментарии отдельно от обещания полной истории. |
| GitHub    | Код, PR, review и обсуждения выбранного проекта; вклад автора отдельно от чужого и сгенерированного кода.                                  |

Для первого варианта не нужен новый MCP-сервер или изменение глобальной конфигурации CLI. STALKER выполняет ограниченный цикл: модель возвращает структурированное следующее действие → контроллер проверяет схему → `SourcePort` вызывает Rust → ограниченный результат становится следующим наблюдением модели. Инструменты описываются типизированными контрактами, например `describe-source`, `search-source`, `collect-resource`, `read-fragment`, `get-coverage`, `finish`. Имена обозначают проектируемые действия, а не существующие команды.

Нативный сборщик самостоятельно обрабатывает страницы API и сохраняет checkpoints; модель не должна тратить отдельный вызов на каждую техническую страницу. Она выбирает материал и дополнительные запросы, получает ссылки на локальные документы, краткие результаты и покрытие. Контроллер ограничивает количество шагов, объём чтения и время; пользователь может отменить работу. Незавершённое задание возвращает частичный результат с причиной, а не заявление о полном исследовании.

Разрешение фиксируется до запуска: аккаунт, конкретный чат/пост/страница/репозиторий, период и разрешённая передача выбранного материала настроенному модельному провайдеру. В этих пределах агент работает без подтверждения каждой страницы. Новые источники требуют расширения выбранной области. Rust повторно проверяет область каждого действия. В инструментах нет произвольного HTTP, shell, отправки сообщений, удаления, чтения секретов или браузерных cookies. Текст источника никогда не становится новой инструкцией навыка.

Контракт `SourceGrant` фиксирует ресурсы, операции, период, срок действия и общие лимиты задания; `CollectionAction` описывает предложенное действие. Ограничения действуют и после повторов/возобновления. Выбор чата выполняется по минимальным метаданным в интерфейсе: модель не получает все диалоги аккаунта для поиска человека. Чужие комментарии, собственные публикации и связанные обсуждения включаются в область явно. Работа с предоставленной личной перепиской расширяет текущий режим public-only и требует соответствующего обновления продуктовых контрактов при реализации.

В режиме сбора CLI получает только выдачу контроллера и не имеет собственных сетевых или терминальных инструментов. Последующий анализ импортированного корпуса также выполняется с инструментами выключенными. Существующий публичный web research остаётся отдельным явно выбранным режимом. При реализации права задаются типом операции, а не распознаванием начала промпта STALKER.

Это требование к будущим адаптерам, а не гарантия JSON-схемы: необходимо подтвердить, что запуск каждого поддерживаемого CLI действительно отключает его инструменты и не наследует пользовательские MCP-подключения. Если такой режим не подтверждён, обработка личного корпуса этим адаптером недоступна. Сетевое обращение самого CLI к выбранному модельному провайдеру сохраняется.

## От корпуса к архетипу

Каждый документ хранит источник, ресурс, автора, дату, время получения, связь с ответом/пересылкой, хеш и статус загрузки. Отчёт о покрытии содержит прочитанные диапазоны, число загруженных и разобранных объектов, пропуски, ошибки и известность общего количества. Получение сообщения подтверждает происхождение текста, но не истинность изложенного в нём.

В пределах выбранного и доступного корпуса выполняется полный проход порциями с сохранением прогресса. Поиск по корпусу дополняет этот проход. Извлечённые свидетельства связываются с конкретными фрагментами; противоречия и недостаток данных сохраняются. Вложения, не прошедшие OCR/распознавание, помечаются как необработанные и не считаются изученными.

Перед модельным анализом известные прямые идентификаторы заменяются локальными псевдонимами; исходный текст остаётся в корпусе для просмотра оснований. Модель работает с ограниченными порциями и непрозрачными ссылками. Такая подготовка снижает объём раскрываемых данных, но не гарантирует удаления всех косвенных идентификаторов из смысла сообщения.

Далее удаляются прямые идентификаторы, и Person Fabric получает обезличенные свидетельства. Результат разделяется на поведенческие правила, наблюдаемые признаки навыков и гипотезы. Отдельная адаптация к задаче по-прежнему одинакова для персон и нейтрального контроля. Навык решения задачи не выдаётся за доказанное умение человека; формула BSC не меняется.

Корпус хранится отдельно от результата эксперимента. Результат содержит версию снимка, ссылки, покрытие и свидетельства. Текущие лимиты контекста, 30 Evidence и форматы JSON v2/пресета v1 нельзя молча использовать для произвольного объёма: расширение требует версии контрактов, миграции и ограничений экспорта. Автоматического включения всей личной переписки в экспорт нет.

## Манера рассуждать и оформление речи персоны

Обязательная цель — воспроизводить наблюдаемую манеру ответа максимально близко к собственным диалогам и комментариям персоны, включая оформление. Для исходных образцов «1 в 1» означает проверяемое сохранение полученного текста и границ реплик. Для нового ответа сходство проверяется отдельно: нельзя гарантировать совпадение с неизвестным будущим ответом человека или объявлять его внутреннее мышление скопированным. Анализируются только приёмы рассуждения, проявленные в тексте, и явно изложенные объяснения; приватные reasoning-потоки модели не становятся «мыслями персоны».

Профиль расширяется отдельным `PersonaStyleProfile`, который Person Fabric составляет без знания экспериментальной задачи:

| Часть профиля                  | Что извлекается из авторских реплик                                                                                                                                                                                |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Наблюдаемые приёмы рассуждения | Порядок аргументов, переход от примера к выводу, уточняющие вопросы, объяснение причин, работа с возражениями, способ выражать сомнения и менять позицию. Для каждого правила — основания, контекст и ограничения. |
| Манера речи                    | Словарь, сленг, сокращения, обращения, юмор, ирония, степень прямоты, характерная лексика и переключения языка. Случайный оборот не становится обязательным для каждого ответа.                                    |
| Формат                         | Регистр, пунктуация, отсутствие точки, повторение знаков, эмодзи и текстовые смайлы, пробелы, переносы строк, абзацы, списки, цитаты, Markdown, длина и разделение сообщения на несколько реплик.                  |
| Режим общения                  | Отдельные варианты для диалога, публичного комментария, review и ответа на задачу. Различия по собеседнику, теме и периоду сохраняются; при недостатке примеров режим помечается как неподтверждённый.             |

Корпус хранит `raw-text` в том виде, в котором текст получен от источника, отдельно от нормализованного поискового представления. В сохранённом оригинале не выполняются `trim`, исправление орфографии, замена кавычек, Unicode-нормализация или перестройка абзацев. Сохраняются последовательность реплик, вложенность ответов, доступные сведения о редактировании и форматные сущности источника. Неизвестная история правок не восстанавливается догадкой. Автоматический перенос по ширине окна не считается авторским переводом строки.

Собственная речь автора отделяется от цитат, пересылок, вставленного кода и сообщений собеседника. Соседние реплики нужны для понимания реакции, но их стиль не приписывается персоне. Навыки сбора обязаны сохранять этот контекст и точное оформление, а также искать повторяющиеся и противоречащие примеры в пределах разрешённого корпуса. Недостаток диалогов или комментариев остаётся видимым ограничением профиля.

Одних кратких описаний стиля недостаточно для запланированной архитектуры: вводится отдельный набор `StyleExemplar` — короткие разрешённые обезличенные образцы с контекстом, режимом общения и ссылкой на происхождение. Они проходят специальную границу подготовки: имена, handles, URL и другие известные прямые идентификаторы заменяются, остальное оформление сохраняется. Изменённые участки отмечаются и исключаются из точного сравнения стиля. Полные исходные переписки остаются в локальном корпусе.

Это явное расширение текущего правила Fabric «только summaries, без исходных цитат»: фактические Evidence сохраняют прежнюю границу, а образцы стиля поступают по отдельному ограниченному и проверяемому контракту. Текст примера всегда является данными, в том числе если внутри написана команда агенту. Экспорт образцов учитывает разрешение на их передачу; полный корпус и идентификаторы не включаются в артефакты персоны автоматически.

Целевые поля профиля: `reasoning-patterns`, `voice-rules`, `format-rules`, `context-modes`, `style-exemplar-ids`, сведения о покрытии и ограничениях. Правила содержат ссылки на конкретные образцы и статус наблюдения или гипотезы. Профиль, выбранные образцы, режим общения и версия инструкции фиксируются до экспериментальных ответов и остаются неизменными между повторами. Подбор примеров не использует будущий эталонный ответ или материалы оценочного набора.

Person получает задачу, навыки, профиль стиля и фиксированные образцы совместно. Требуемое оформление формируется сразу при генерации. Автоматическая литературная правка, добавление стандартных заголовков, списков и заключений не входит в этот путь. Небрежность, разговорная лексика и короткие реплики сохраняются там, где они подтверждены выбранным режимом. Явный формат задания, например обязательный JSON или исполняемый код, соблюдается; конфликт с привычками персоны отмечается в метаданных соответствия стилю.

Для диалога проектируется `PersonReply` с массивом сообщений, сохраняющим каждую реплику и её точный текст. Валидатор проверяет тип и ограничения размера без переписывания содержимого; UI отображает текст безопасно, с сохранением пробелов и переносов, не выполняя HTML из источника. Маркировка симуляции и метаданные находятся вне текста реплики. Версионированный контракт задаёт также текстовое представление для судьи и экспорта; границы сообщений остаются доступны и не теряются при преобразовании в прежнее поле `answer`.

Текущий `personRuntime` возвращает одну строку, а `text()` в Intelligence выполняет `trim()`. Общая инструкция требует русский язык и запрещает Markdown без разделения JSON-контейнера и содержимого строки; пагинация UI добавляет переносы и обрезает пробелы в начале переносимой части. При реализации новый контракт требует отдельного валидатора без потерь, сохранения языка выбранного режима, точного отображения, обновления Person, артефактов `AGENTS.md`/`SKILL.md`, сохранения и совместимости результатов. Запрет Markdown-обёртки вокруг JSON не должен запрещать авторский Markdown внутри текста ответа. Это пока проектируемое поведение; существующие ответы не объявляются точными копиями стиля.

## Проверка сходства с персоной

Проверка стиля отделена от Brain Scoring: BSC продолжает измерять выполнение задачи. Новый отчёт показывает сходство оформления, характерных оборотов и наблюдаемых приёмов рассуждения по отдельности, с примерами расхождений и покрытием. Он не называется точностью копирования мозга и не повышает оценку навыков человека.

До извлечения фактических свидетельств и стиля корпус делится на материал для построения и отложенные диалоги/ветки для оценки; дубли и части одной ветки не пересекают границу. В оценочном сценарии модели доступен предшествующий контекст, а реальная проверяемая реплика скрыта до получения ответа. Оценочные ветки не попадают в профиль, фактические summaries, подбор образцов или поиск сборщика. Отчёт о покрытии отдельно показывает намеренно отложенные материалы; они не объявляются изученными для построения персоны. Настройка по результатам требует отдельного набора проверки, чтобы не подгонять профиль под один и тот же эталон.

Сохранение и отображение исходного текста проверяются точным сравнением; для новых ответов оцениваются распределения длины реплик, регистра, пунктуации, эмодзи, абзацев и разделения на сообщения. Их содержательность и сходство аргументации проверяются отдельно на отложенных примерах. Буквальное повторение сохранённого образца не считается доказательством воспроизведения манеры рассуждать. Малый или однородный набор не даёт основания выводить универсальный процент сходства.

Проверка не исправляет смысл готового ответа, не запускает скрытый подбор лучшей попытки и не меняет замороженную персону во время эксперимента. Использование модельного оценщика отражается в traces и затратах. Нейтральный контроль сохраняет нейтральный стиль, общий формат задания и одинаковую политику генерации/повторов; отдельного преимущества в числе попыток у персон нет.

## Этапы реализации и критерии готовности

1. `contracts` и нативная служба: области доступа, задачи загрузки, документы, покрытие, хранилище и mock-адаптеры. Проверить изоляцию аккаунтов, отмену, продолжение и отсутствие секретов в результатах.
2. Навыки STALKER и контроллер: ограниченный цикл действий; тесты выхода за область, повторов, превышения бюджета и инструкций внутри источника. Без настроенного адаптера — явная ошибка.
3. TDLib и импорт: реальное подключение, полный проход выбранной доступной истории, атрибуция, checkpoints, fixtures экспортов.
4. `apps/auth`, deep links, VK и единая публикация: положительный PKCE обмен на реальном HTTPS адресе; чужой, повторный, просроченный callback отвергается; импорт `.proteus` продолжает работать.
5. GitHub, Instagram собственного профессионального аккаунта и отдельная проверка WebView. Возможность встроенного чтения Instagram считается экспериментальной до проверки реального сайта на поддерживаемых ОС.
6. Профиль манеры рассуждать и речи: сохранение оригинальных реплик, атрибуция автора, отдельные режимы, обезличенные образцы и их происхождение. Тесты на изменение пробелов, пунктуации, эмодзи, Unicode, цитат и границ сообщений; модель не получает исходные идентификаторы через образцы.
7. Person и отображение: применение замороженного стиля, поддержка нескольких реплик, отсутствие автоматической правки текста, совместимость сохранения и экспорта. Проверить обязательный формат задачи и нейтральный контроль.
8. Полный сценарий corpus → Evidence / StyleExemplar → Fabric → Person; все доступные выбранные порции учтены, пропуски видны, ссылки на происхождение сохранены, модель не получает credential storage. Отдельная оценка стиля на отложенных ветках без утечки в профиль и без изменения BSC.

FSD, выборочная сборка, Stylelint и Playwright расширены на `apps/auth`; запрещённые импорты и пропуск проверки нового приложения покрыты negative fixtures. Применяются проверки пакетов и зависимых пакетов, общий gate, а для реализации нативной части — Rust tests и desktop build. Проверка статической модели и SPA не заменяет живой тест авторизации.

Beads CLI в текущем окружении отсутствует. Этот список служит конкретной передачей работ; issue IDs и синхронизация задач не заявляются. После появления `bd` задачи заводятся по установленному workflow и экспортируются штатной командой.
